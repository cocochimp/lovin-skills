# 规格提案

将探索阶段的结论正式化为决策文档：提案（做什么）+ 任务（谁做）。

REQUIRED SUB-SKILL: spec-detail（后续阶段：基于本技能产出生成详细功能规格）

**职责边界**：本技能负责提案和任务定义，不负责详细的功能规格（那是 spec-detail 的职责）。

**与 spec-explore 的关系**：
- `spec-explore` 输出**探索笔记**（探索过程 + 设计结论一体化，包含架构决策、领域建模、接口设计、时序图等）
- `spec-proposal` 从探索笔记中提取**决策快照**（proposal.md）和**任务分配**（tasks.md）
- 两者可反复迭代：spec-proposal 发现探索不充分时退回 spec-explore 继续探索

## When NOT to Use

- 已有明确的功能规格，只需实施时 → 使用 `spec-detail`
- 仅探索创意、头脑风暴阶段 → 使用 `spec-explore`

## 核心概念

- **功能（Feature）**：一个完整的业务用例（User Case），具备端到端的业务闭环。可能跨越多个系统和方法，但对外呈现为一个完整的业务能力。
  - ✅ 正确粒度：`create-order`（UC4 创建订单：采购商→btrade→sell→buy→供应商 全链路）
  - ✅ 正确粒度：`search-availability`（UC2 查询报价：采购商→bsearch→item→goods→供应商 全链路）
  - ❌ 错误粒度：`sell-create-order`（只是 UC4 在 sell 系统内的一个步骤，不是完整用例）
  - ❌ 错误粒度：`order-module`（模块级别，不是具体用例）
  - **判断标准**：一个功能必须从触发方的视角出发，具备完整的业务闭环（有明确的触发、处理、结果）。
- **任务**：由 PM 分配给研发/团队的工作单元。分为**基础任务**（跨 UC 的公共依赖）和**功能任务**（一个 UC = 一个任务）。任务描述业务需求（做什么），不描述实现方式（怎么做）。

## 文档流水线

```
探索笔记（探索过程 + 设计结论）
    → 提案（为什么 & 做什么，含功能清单）
        → 任务（基础任务 + 功能任务，描述业务需求，分配给人）
```

每个文档在前一个的基础上构建。proposal 是对探索笔记的**决策快照提炼**，tasks 是基于 proposal 的**任务分配**。

## 指引

### 阶段 0：承接探索笔记

**必须先读探索笔记** — 查找 `specs/*/exploration-notes.md`，完整阅读。探索笔记是本技能的核心输入，包含了问题定义、架构决策、UC 清单、领域建模、接口设计等深度内容。

**从探索笔记中提取：**

| 探索笔记章节 | 提取到 | 说明 |
|---|---|---|
| 问题域和业务背景 | proposal.md → 问题陈述 + 目标用户 | 压缩为 2-3 句话 |
| 物理应用架构 | proposal.md → 系统全景 | 简要引用 |
| 一期范围和 User Case | proposal.md → 功能清单 + tasks.md → 任务列表 | 每个 UC = 一个功能任务；跨 UC 公共依赖 = 基础任务 |
| 待解决问题 | proposal.md → 不在范围内 | 明确排除的内容 |

**确定输出目录** — proposal.md 和 tasks.md 写入探索笔记所在的同一目录（即 `specs/<变更名称>/`，与 `exploration-notes.md` 同级）。不要新建目录。

**增量更新模式** — 当 proposal.md 和 tasks.md 已存在时（说明之前执行过本技能），进入增量更新流程：

1. 完整读取当前 `exploration-notes.md`、已有 `proposal.md`、已有 `tasks.md`
2. 识别探索笔记与已有文档的不一致：
   - 新增/删除/合并了 UC → 影响 proposal 功能清单 + tasks 功能任务
   - 新增了跨 UC 的公共依赖（如新共享模型、新中间件方案、新接口契约）→ 影响 tasks 基础任务
   - 探索笔记"已解决问题"中有新条目，而 proposal "不在范围内"仍排除着它
   - 决策变更导致已有任务描述或依赖关系需调整
3. **展示变更摘要**给用户确认（列出新增/修改/删除项），等待用户确认后再执行更新
4. 用户确认后，仅更新受影响的部分，保留用户可能手动调整过的内容

**首次生成模式** — 当 proposal.md 和 tasks.md 不存在时，按阶段 1→2 顺序生成。

**如果没有探索笔记**（用户直接使用本技能），提出澄清问题：
- 你想解决什么问题？
- 目标用户是谁？
- 预期范围是什么（新功能 / 修改 / 移除）？
- 建议先使用 `spec-explore` 进行探索。

**探索笔记充分性判断** — 至少需要以下内容才能继续：

| 必要章节 | 判断标准 | 缺失影响 |
|----------|----------|----------|
| 问题域和业务背景 | 有明确的系统定位和业务模式描述 | 无法写 proposal 的问题陈述 |
| 一期范围和 User Case | 有 UC 清单（至少列出 UC 编号 + 触发方 + 说明） | 无法定义功能清单和任务 |

缺失任何一项则建议退回 `spec-explore` 补充。其他章节（架构决策、领域建模、接口设计、时序图等）是 spec-detail 阶段的输入，不阻塞本技能。

**在没有清晰理解变更之前，不要继续推进。**

### 阶段 1：提案 (`proposal.md`)

将探索笔记中的问题定义和范围决策正式化为提案文档（信息来源见阶段 0 映射表）。

**模板：**

```markdown
# 提案：<变更名称>

## 问题陈述

<!-- 2-3 句话：这解决什么问题？为什么是现在？不做会有什么影响？ -->

## 目标用户

<!-- 谁从这项变更中受益？简要描述用户画像。 -->

## 系统全景

<!-- 涉及的系统/应用/模块概览，让读者快速了解整体架构。引用探索笔记中的物理应用架构。 -->

## 功能清单

<!-- 
  每个功能 = 一个完整的 UC（User Case），具备端到端业务闭环。
  格式：UC编号 + 触发方 + 涉及系统 + 业务描述。
  用 **破坏性变更** 标记不兼容的变更。
-->

### 新增功能

| UC | 功能名 | 触发方 | 涉及系统 | 业务描述 |
|----|--------|--------|----------|----------|
| UC1 | `<kebab-case-名称>` | 用户/系统 | sys1 → sys2 → sys3 | <完整业务描述> |

### 修改功能
<!-- 同上格式，标注修改原因 -->

### 移除功能
<!-- 功能名 + 移除原因 -->

## 影响分析

<!-- 受影响的系统、API、数据模型、外部依赖 -->

## 成功标准

<!-- 如何知道这项变更成功了？列出 2-4 个可衡量的结果，可包含业务和技术两方面。 -->

## 不在范围内

<!-- 明确列出不包含的内容，防止范围蔓延。包括探索笔记中标注为后续阶段的内容。 -->
```

**指导原则：**
- 保持简洁（1-2 页）。聚焦于"为什么"和"做什么"，而非"怎么做"。
- 功能清单至关重要——每个功能将成为 tasks.md 中的一个功能任务，分配给研发后由 `spec-detail` 生成详细规格。
- **强制校验**：写完功能清单后，逐条检查每个功能是否具备完整的业务闭环（有触发、有处理、有结果）。不满足则合并或重新定义。
- 成功标准应是可衡量的（如"采购商可通过 API 完成全链路交易"、"创单 RT < 3s"）。
- 如果探索笔记中有明确的 UC 清单，直接提取为功能清单，无需重新发明。

### 阶段 2：任务 (`tasks.md`)

基于提案中的功能清单，将每个功能（UC）定义为一个任务。

**任务分两类：**

| 类型 | 定义 | 来源 |
|------|------|------|
| **基础任务** | 被多个 UC 共享的公共依赖，必须提前统一 | 从探索笔记中识别跨 UC 的公共部分 |
| **功能任务** | 一个完整的 UC，端到端业务闭环 | 提案中的功能清单，一个功能 = 一个任务 |

**基础任务识别与拆分规则**：

被 2 个以上 UC 共享且需提前统一的东西 = 基础任务。每个独立成一条，禁止合并。

**识别方法**：遍历 UC 清单，提取所有涉及的域/系统/共享依赖，凡被多个 UC 使用的就抽为基础任务。特别注意：

- **各域领域模型**：统计每个域被几个 UC 使用，≥2 个就必须作为独立基础任务。覆盖范围根据该域的 DDD 模式决定（写模式关注聚合根/状态机/方法签名，纯计算模式关注共享数据模型和核心 Param/Result），不包括 DomainService、AppService 等编排层——这些在功能任务中按 UC 语境设计。
- **跨域共享模型**：被多域复用的值对象/枚举，单独一个基础任务。
- **域间接口契约**：依赖各域模型完成后定义，独立一个基础任务。
- **其他常见类型**：工程脚手架、防腐层接口定义、中间件基础设施、统一鉴权方案等。

**核心规则：**
- 所有任务统一用数字编号（1, 2, 3…），基础任务在前，功能任务接着编
- 需求描述说清"要实现/统一什么"，不描述实现步骤
- 依赖关系精确到具体任务编号
- 任务由本阶段定义和管理（新增、删除、重排），后续 `spec-detail` 不可新增或删除任务

**模板：**

```markdown
# 任务：<变更名称>

<!-- 基础任务：跨 UC 的公共依赖，每种类型独立一个任务 -->

## 1. <基础任务名>（依赖：无）

- **状态**：待分配
- **负责人**：待定
- **需求**：<统一定义什么，解决什么对齐问题>
- **下一步**：spec-detail → specs/<任务名>/spec.md

## 2. <基础任务名>（依赖：任务 1）

- **状态**：待分配
- **负责人**：待定
- **需求**：<统一定义什么，解决什么对齐问题>
- **下一步**：spec-detail → specs/<任务名>/spec.md

<!-- 功能任务：每个 UC 一个任务 -->

## 3. <UC名称>（依赖：任务 1, 2）

- **状态**：待分配
- **负责人**：待定
- **需求**：<业务需求描述>
- **下一步**：spec-detail → specs/<功能名>/spec.md
```

**指导原则：**
- 先识别基础任务，再列功能任务（每个 UC 一个）。
- 按依赖关系排序。功能任务之间如有依赖也需标注。
- 初始状态为"待分配"，PM 分配后更新负责人，完成后更新状态为"已完成"。

## 输出结构

所有文档写入 `specs/<变更名称>/` 目录：

```
specs/<变更名称>/
├── exploration-notes.md  （来自 spec-explore，探索 + 设计结论）
├── proposal.md           （提案：为什么 + 做什么）
└── tasks.md              （任务：谁做 + 业务需求）
```

## 完成摘要

生成所有文档后，提供：

```
## 规划完成：<变更名称>

**已创建的文档：**
- proposal.md — 问题陈述、N 个功能（UC）、成功标准
- tasks.md — 基础任务 + N 个功能任务，每个任务描述业务需求

**下一步：** PM 将任务分配给研发，研发使用 `spec-detail` 基于探索笔记生成详细功能规格。
```

## 与 spec-explore 的迭代

spec-proposal 执行过程中可能发现探索不充分，需要退回 spec-explore：

| 信号 | 行动 |
|------|------|
| 探索笔记中待解决问题阻塞了任务定义 | 标注阻塞项，建议退回 spec-explore 解决后再来 |
| 功能清单中某个 UC 的范围不清晰 | 建议退回 spec-explore 澄清 UC 边界 |
| 用户在 review 时提出新问题 | 记录问题，建议用 spec-explore 探索后更新 |

退回时在 exploration-notes.md 的「待解决问题」中追加新问题，保持问题编号递增。

**必须在退回前告知用户并获得确认，不得自行决定退回。**

## 护栏规则

- 按顺序创建：提案 → 任务，每个文档基于前一个构建
- 如果上下文不清楚，询问用户——但优先做合理假设以保持进度
- **退出条件**：如果探索笔记不存在且经过 2 轮澄清后用户仍无法明确核心需求（问题陈述 + 至少 1 个功能），停止流程并建议用户先使用 `spec-explore` 进行探索
