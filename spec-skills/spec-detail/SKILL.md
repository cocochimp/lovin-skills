# 功能规格生成

将 PM 分配的任务拆解为 AI 可直接编码的实现规格。

## 定位

PM 产出 UC 级全局视角（系统间怎么协作），AI 编码需要领域级局部视角（每个领域对象做什么）。spec-detail 填补这个粒度鸿沟。

**spec.md = AI 编码的单一信息源**。拿到它后 AI 结合 DDD rules 和基础 spec 就能完成编码——所以它必须包含领域对象职责、业务规则和验收场景。

### spec 用领域语言描述业务

spec 使用 DDD 的概念体系作为"词汇表"——聚合根、值对象、领域服务等术语既是业务概念也是代码结构，产品和开发能用同一套语言沟通。**spec 描述的是业务（谁做什么），不是代码（哪个类调哪个方法）**。

Repository、Adaptor、Infrastructure 等技术实现细节**不出现在 spec 中**——它们由编码阶段的 AI 根据 DDD rules 自行推导。

### AI 编码需要三样东西

| # | 需要什么 | spec 中对应 | 没有会怎样 |
|---|----------|------------|-----------|
| 1 | **谁做什么**（领域对象 + 职责） | 参与的领域对象及职责 | 不知道代码放在哪个类 |
| 2 | **逻辑**（内部做什么、分支条件） | 业务规则 | 写出来的代码是猜的 |
| 3 | **验收**（怎么判断写对了） | 场景(GIVEN/WHEN/THEN) | happy path 能跑，边界出 bug |

**业务规则 = 实现指南（告诉 AI 怎么写）。场景 = 验收标准（告诉 AI 写对没有）。两者配对出现。**

**上下游**：`spec-explore`/`spec-proposal` → **spec-detail** → 编码技能

## 两种任务类型

| 类型 | 定义 | spec 侧重 |
|------|------|-----------|
| **基础任务** | 跨 UC 公共依赖（领域模型） | 字段、状态机、方法签名、通用校验 |
| **功能任务** | 一个完整 UC，端到端跨系统 | 功能元信息 + 全局时序 + 领域对象职责 + 业务规则 + 场景 |

一个任务 = 一个 spec.md。基础任务定义"是什么"（纯签名），功能任务定义"怎么流转"（所有业务逻辑）。

**基础任务只做签名**——字段、方法名、参数类型、返回值、状态机流转图。不写任何业务规则、校验逻辑或场景。原因：做基础任务时还不清楚所有 UC 怎么用这个模型，强行写"通用规则"大概率要改；业务规则只有在具体 UC 语境下才有意义。

**所有业务逻辑都在功能任务中完成**——包括聚合根方法的前置校验、状态变更条件、计算公式。功能 spec 通过"参与的领域对象及职责"章节列出本功能涉及的领域对象（引用基础 spec 中的全局定义，不重复定义字段），然后在"业务规则"章节为这些对象的行为写出完整的业务逻辑。

## 交互原则

你是有判断力的技术搭档，不是记录员。用户的时间花在**判断**上，你负责**生成+主动挑战**。

**工作节奏**：加载上下文 → 推导草案 → 展示+标注置信度 → 用户确认 → 写入 → 推进下一部分。

### 分段确认机制

**每个域的规则+场景写完后必须暂停**，等用户确认后再推进下一个域。具体节奏：

1. **领域对象及职责**：写完直接展示，用户快速过（从基础 spec 和探索笔记推导，确定性高）
2. **业务规则**：写完后**暂停确认**。展示草案时：
   - 标注哪些规则是"探索笔记明确定义的"（✅ 高置信）vs"我推导的"（⚠️ 需确认）
   - 对推导出的规则，主动问一个聚焦问题（不是"你觉得怎么样？"而是具体的歧义点）
   - 问"还有没有遗漏的判断条件或边界？"
3. **场景**：写完后**暂停确认**。问"还有没有需要验证的 case？"

### 主动挑战

对自己推导的规则保持怀疑：
- 探索笔记用了模糊措辞（"通常"、"一般"）→ 主动追问具体行为
- 多种合理实现都说得通 → 列出选项让用户拍板
- 规则涉及异常/并发/空值 → 主动提出边界场景问用户

### 不纠缠的事

- 偏好性问题（命名风格、错误码措辞）
- 探索笔记中已明确决策的结论（不重复质疑）
- 领域对象的 DDD 角色划分（规范已定义，不需要用户确认）

## 执行流程

### 启动

用户指定任务编号时直接开始，未指定时列出未完成任务供选择。

### 阶段 0：加载上下文

按以下顺序读取，全部加载后才能产出草案（没有上下文的草案大概率是错的）：

1. `specs/<变更名称>/exploration-notes.md` — 最重要的输入，含架构决策和设计结论
2. `specs/<变更名称>/tasks.md` — 当前任务定义和依赖关系
3. 按 CLAUDE.md §规则加载 的 **spec-detail** 行加载 DDD rules — 领域对象角色和命名必须符合 V3 规范（`ddd-architecture-overview.md` §1.5 分层 Bean 表是后缀和基类的强约束来源）
4. 依赖的基础任务 spec — 如未完成，提示用户并标注依赖待确认
5. CodeGraph 读取已有代码 — 理解可复用模式和衔接点

**续写判断**：如果目标 spec.md 已存在且头部有 `status: draft`，读取已完成部分，识别缺失章节，从断点继续。

### 阶段 1：逐步产出（功能任务）

每完成一步，立即写入 spec.md——不要攒到最后，上下文可能中途丢失。

| 步骤 | 产出 | 落盘时机 |
|------|------|----------|
| 1. 确认范围 | 功能元信息（名称、开发模式、接口入口） | 写入"功能元信息"章节 |
| 2. 全局时序 | PlantUML 系统间时序图 | 写入"全局时序"章节 |
| 3. 逐域领域对象及职责 | 参与对象表 + 从属关系 | 每个域确认后立即写入 |
| 4. 逐域业务规则 | 规则描述（见下方粒度判断） | 同上 |
| 5. 逐域场景 | GIVEN/WHEN/THEN 验收标准 | 同上 |
| 6. 领域事件 | 事件触发、消费者、后续动作 | 写入"领域事件"章节 |
| 7. 约束 | 非功能性需求 | 写入"约束"章节 |

产出领域对象职责时，持续对照 DDD rules：确保对象角色（聚合根/实体/值对象/领域服务）和开发模式匹配。发现不符合规范时主动指出并调整。

#### 业务规则粒度判断

不是每个领域行为都需要写规则。判断标准：

| 行为类型 | 需要写规则吗 | 原因 |
|----------|-------------|------|
| 纯数据承载（值对象字段映射） | ❌ 不需要 | AI 从签名就能推断 |
| 简单查询（按 ID 查询聚合根） | ❌ 不需要 | 同上 |
| 有业务判断的（校验、规则匹配、筛选策略） | ✅ 必须写 | AI 无法从行为名猜出判断条件 |
| 有计算的（加价、币种转换、最低价） | ✅ 必须写 | AI 无法猜出公式 |
| 有状态流转的（聚合根状态变更） | ✅ 必须写 | AI 无法猜出前置条件和状态变更 |

**原则：如果 AI 只靠领域对象名+行为名无法写出正确实现，就必须写规则。**

#### 业务规则表达方式

根据规则类型选择最清晰的表达方式：

| 表达方式 | 适合什么规则 | 格式示例 |
|----------|-------------|---------|
| **校验表** | 参数校验、前置条件 | 字段 / 规则 / 错误码 三列表格 |
| **决策表** | 多条件组合 → 结果 | 条件1 × 条件2 → 输出 |
| **有序步骤** | 有明确顺序的编排逻辑 | 1. 做A 2. 做B 3. 做C |
| **规则条目** | if/匹配/优先级类逻辑 | 自然语言描述匹配和优先级规则 |
| **公式** | 计算类 | `result = input × factor` |
| **约束声明** | 不变量/边界 | "X 全局唯一，格式为 UUID v4" |

#### 业务规则标准结构

每条规则包含：

```
#### 规则：BR-<域>-<编号> <名称>

**归属**：<领域对象名>（角色） — 一句话说明这是哪个领域对象的什么行为

**输入**：规则判断需要的数据

**逻辑**：（从上述的几种[业务规则表达方式]中选择最清晰的表达方式）

**边界**：异常/空值/并发等边界情况的处理
```

**规则归属到领域对象**：规则的归属写领域对象名称和角色（如"SellOrder（聚合根）"、"BuildItemOfferDomainService（领域服务）"），不写具体代码方法名。编码阶段的 AI 根据 DDD rules 自行决定放在哪个方法中。

### 阶段 1：逐步产出（基础任务）

基础任务只产出签名级信息，不写业务规则和场景。**产出范围严格以 task 描述为准**——task 说什么层就只产出什么层，不自行扩展到 task 未提及的层或模块。

| 步骤 | 产出 | 落盘时机 |
|------|------|----------|
| 1. 确认范围 | 支撑哪些 UC、task 描述覆盖哪些层/模块 | 写入"目标"章节 |
| 2. 模型定义 | 仅 task 指定范围内的字段表、状态机流转图、方法签名表（方法名+参数+返回值+一句话行为描述） | 确认后立即写入 |
| 3. 约束 | 仅非功能性约束（如 ID 格式、字段长度） | 同上 |

不写业务规则、不写场景。业务逻辑在功能任务 spec 中按 UC 语境完成。

### 阶段 2：收尾

1. 移除整个 YAML front matter 块（即开头的 `---`、`status: draft`、闭合的 `---` 三行全部删除），确保文件以 `#` 标题开头
2. 一致性检查：系统间输入输出对齐、模型引用正确
3. 告知用户 spec 完成，可进入编码阶段

## 输入与输出

**输入（全部只读）**：
- `specs/<变更名称>/exploration-notes.md`
- `specs/<变更名称>/proposal.md`
- `specs/<变更名称>/tasks.md`
- `.aone_copilot/rules/`
- 已有代码（CodeGraph）和已完成的 spec

**输出**：`specs/<变更名称>/<任务名>/spec.md`。

## 护栏

- **先读后写**：加载 exploration-notes.md + DDD rules 后才产出草案。没有上下文就动笔会浪费所有人的时间。
- **只产规格不写代码**：这是设计阶段。输出到 spec.md 为止。
- **PM 文档只读**：exploration-notes.md、proposal.md、tasks.md 不可修改。发现问题标记在 spec 中，告知用户线下沟通。
- **领域对象角色遵循 DDD rules**：聚合根、实体、值对象、领域服务的职责划分必须符合 DDD 规范。**产出每个领域对象时，逐个对照 `ddd-architecture-overview.mdc` §1.5 的 Java Bean 后缀表检查**，无后缀的裸名类不合法。
- **spec 不暴露技术实现**：Repository、Adaptor、Infrastructure、Cache 等技术组件不出现在 spec 中。它们由编码阶段的 AI 根据 DDD rules 自行推导。
- **领域模型引用全局定义**：功能 spec 中不重复定义领域对象的字段和签名——这些在基础 spec 中全局维护。功能 spec 只描述对象在本功能中的职责。编码 AI 需同时读取基础 spec 获取完整定义。
- **确认外部依赖细节**：功能涉及调用外部服务时，必须向用户确认外部接口的具体入参、出参、调用方式等细节，不要假设或推导。
- **确认跨系统交互形式**：涉及多系统协作时，必须向用户确认系统间的交互协议（HSF/HTTP/MQ/回调等）和数据契约，不要默认。
- **规则先于场景**：先写业务规则（实现指南），再写场景（验收标准）。规则告诉 AI 怎么写，场景告诉 AI 写对没有。
- **规则不是伪代码**：用校验表、决策表、公式、有序步骤等声明式方式表达，不写 if/else 伪代码。
- **只为非显而易见的行为写规则**：纯数据承载、简单查询不需要规则。有业务判断/计算/状态流转的领域行为才需要。
- **场景可测试**：每个 GIVEN/WHEN/THEN 必须能映射到一个测试用例。写不出测试 = 需求太模糊，追问用户。
- **编码 AI 组合读取**：编码阶段的 AI 需同时读取功能 spec（职责+规则+场景）和基础 spec（字段+签名），两者组合构成完整信息。功能 spec 不重复基础 spec 的内容，避免维护地狱。
